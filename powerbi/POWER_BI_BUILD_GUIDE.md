# Power BI Build Guide — SQL-backed Retail Dashboard

This package is the output of the full pipeline: **messy Excel → Python cleaning →
SQLite database (`business.db`) → SQL views → this folder**. Two ways to bring it into
Power BI, pick whichever fits your setup.

## Option A — Connect live to the SQLite database (recommended)
Power BI doesn't ship a native SQLite connector, so it goes through ODBC:
1. Install the SQLite ODBC driver (search "SQLite ODBC Driver", the `ch-werner` build is
   the common free one) and create a System DSN pointing at `business.db`.
2. In Power BI Desktop: `Get Data → ODBC → (select the DSN)`.
3. You'll see the `sales` table plus every view (`v_monthly_kpis`, `v_category_performance`,
   etc.) — import the ones you need. Because the KPI logic already lives in SQL, you don't
   need to rebuild those aggregations in DAX; the views arrive pre-aggregated.

## Option B — Import the CSV exports (simpler, no driver install)
This folder already contains the SQL views exported as CSVs, generated by running the
views against `business.db`:
- `sales_fact.csv` — the cleaned transaction-level fact table (1,964 rows)
- `v_monthly_kpis.csv` — revenue/profit/margin/AOV by month
- `v_category_performance.csv` — same, by product category
- `v_region_performance.csv` — by region
- `v_channel_performance.csv` — Online vs In-Store split
- `v_customer_value.csv` — lifetime revenue/profit per customer
- `v_repeat_purchase_rate.csv` — single-row overall repeat rate

`Get Data → Text/CSV` and import each one. Faster to set up, but static — re-run
`clean_and_load.py` + the SQL script and re-export if the source data changes.

## Data model
If you import `sales_fact.csv` alongside the summary views, relate them on the shared
keys so slicers on one page filter everything:

| From | To | Key |
|---|---|---|
| `sales_fact` | `v_customer_value` | `customer_id` |

The other views (`v_monthly_kpis`, `v_category_performance`, etc.) are pre-aggregated
summaries — use them directly on cards/charts rather than relating them back to the fact
table, since re-aggregating aggregates double-counts.

## DAX measures (only needed if you use `sales_fact` directly, Option A)
```dax
Total Revenue = SUM(sales_fact[revenue])
Total Profit = SUM(sales_fact[profit])
Gross Margin % = DIVIDE([Total Profit], [Total Revenue], 0)
Average Order Value = DIVIDE([Total Revenue], DISTINCTCOUNT(sales_fact[order_id]), 0)
Total Orders = DISTINCTCOUNT(sales_fact[order_id])
Unique Customers = DISTINCTCOUNT(sales_fact[customer_id])
```
If you're using the CSV views instead, these are already computed columns — just drop
`total_revenue`, `gross_margin_pct`, etc. straight onto visuals, no DAX needed.

## Suggested report pages

**Page 1 — Executive Overview**
- Cards: Total Revenue, Total Profit, Gross Margin %, Repeat Purchase Rate (from `v_repeat_purchase_rate`)
- Line chart: `v_monthly_kpis[month]` vs `total_revenue`
- Bar chart: `v_category_performance[category]` vs `total_revenue`

**Page 2 — Regional & Channel Mix**
- Map or bar chart: `v_region_performance`
- Donut chart: `v_channel_performance[pct_of_total_revenue]`

**Page 3 — Customers**
- Table: `v_customer_value` sorted by `lifetime_revenue` descending
- Card: count of customers, total lifetime revenue

## Why this shape
Doing the aggregation in SQL (not DAX, not Python) means the same KPI definition is
reusable from any tool that can query `business.db` — a second dashboard, an analyst
running ad hoc queries, or a scheduled report all read from the same source of truth
instead of three different reimplementations of "what counts as revenue."

## Why no `.pbix` file
Power BI Desktop is a Windows/Mac app with a proprietary binary format that can't be
generated from a script in this environment. This package gives Power BI everything it
needs — a queryable database, pre-aggregated views, exact DAX, and layout — so building
the report is assembly, not a blank canvas.
